# ArchiveLens v1.2 Development Plan

Target version: **1.2.0**

This document defines the v1.2 work after ArchiveLens v1.1.0. The release should expand ArchiveLens from an archive-first comic viewer into a practical local reader for archives, image folders, and PDF documents while preserving the project’s strongest constraints: read-only source handling, local-only operation, ephemeral credentials, bounded resource use, responsive background work, portable Windows packaging, and reproducible release verification.

## 1. Release goal

ArchiveLens v1.2 should focus on **reader continuity and content-source expansion**.

The user-facing target is:

1. Resume reading and recent-reading history.
2. Per-book page bookmarks.
3. Folder reading, including safe recursive subfolder discovery.
4. A generalized content-source layer above the existing archive providers.
5. Additional raster/image formats: AVIF, HEIC/HEIF, TIFF, JPEG XL/JXL, JPEG 2000/JP2 where a tested Windows backend is available.
6. PDF reading through a dedicated PDF provider built on QtPdf rather than pretending PDF pages are archive entries.
7. Fit Width and Fit Height modes.
8. Non-destructive automatic/manual border trimming for scanned pages.
9. Packaging, backend/license records, migration, CI, and manual QA for the expanded feature set.

The release should remain simple for the common case: a user can still drag a CBZ/CBR/ZIP/RAR/7Z into ArchiveLens and start reading immediately without creating a library or account.

## 2. v1.1 baseline that must be preserved

v1.2 builds on the v1.1 architecture and must not regress:

- ZIP/CBZ, 7Z, RAR/CBR providers;
- ZipCrypto/AES ZIP and encrypted 7Z/RAR session password handling;
- read-only source archives;
- no full-archive extraction to a user-visible directory;
- natural ordering;
- background loading and stale-result protection;
- decoded-image and thumbnail bounded caches;
- animated GIF playback;
- thumbnail sidebar;
- single/double page reading;
- first-page cover mode;
- LTR/RTL reading;
- fit, 100%, zoom, rotation, pan, fullscreen;
- portable Windows package and per-user installer;
- backend self-test/release verification;
- credential redaction and no persistent archive passwords.

All v1.1 security/resource guarantees are regression requirements.

## 3. Architecture direction

### 3.1 Add a content-source abstraction above ArchiveProvider

The existing `ArchiveProvider` remains responsible for archive semantics such as entries, compressed/uncompressed sizes, credentials, solid-archive behavior, and byte reads. Do not replace it.

v1.2 should add a higher-level abstraction that represents things the viewer can read, for example:

```text
ContentProvider
├── ArchiveContentProvider
│   └── ArchiveProvider
│       ├── ZipArchiveProvider
│       ├── SevenZipArchiveProvider
│       └── RarArchiveProvider
├── FolderContentProvider
└── PdfContentProvider
```

The exact class names may change after implementation review, but the separation is mandatory: PDF and folders must not be modeled as fake compressed archives merely to reuse the old API.

A content provider should expose stable page descriptors and page-loading capabilities while allowing provider-specific implementations underneath.

Conceptually:

```text
ContentProvider
- open(source, credentials?)
- close()
- list_pages() -> PageDescriptor[]
- load_page(page, request) -> page/media result
- capabilities
```

`PageDescriptor` should contain only cross-source information needed by the reader, such as index, display name/relative path, media kind, and optional size hints. Archive-specific compression fields remain in `ArchiveEntry`.

### 3.2 Keep decode/render paths explicit

Archive and folder raster images naturally provide bytes/files that pass through an image decoder. PDF pages are rendered by the PDF backend into an image at a requested output size.

Avoid a design that requires every content source to return raw bytes.

Recommended flow:

```text
Archive/Folder page -> raster bytes/path -> DecoderRegistry -> decoded image
PDF page            -> PdfContentProvider -> bounded render request -> decoded image
                                              ↓
                                         common viewer/cache
```

The cache layer may need a source-aware cache key. PDF render size/DPI must be part of the cache identity when different render resolutions can exist for one page.

### 3.3 Generalize session credentials carefully

Archive passwords remain in memory only. Password-protected PDF should reuse the same UI principles without persisting credentials.

If a higher-level `SessionCredentials` abstraction is introduced, it must preserve current redaction/lifetime guarantees and must not cause archive passwords to enter settings, logs, command-line arguments, reading history, or bookmark storage.

## 4. Reading-state model

### 4.1 Resume / continue reading

Persist non-sensitive reading state for local content sources.

Minimum state:

- source identity/path;
- current logical page index;
- page count at last close/open;
- last-opened timestamp;
- single/double mode;
- LTR/RTL direction;
- first-page-cover preference when applicable;
- fit mode;
- rotation if rotation is persisted per source.

A source identity should defensively detect obvious file replacement. A practical first implementation may combine canonical path with selected stat data such as file size and modification time for files, and a normalized folder path plus lightweight scan identity for folders.

Do not hash complete large archives/PDFs during normal open merely to create identity.

### 4.2 Recent history

Add a bounded recent-reading history. Store metadata only.

Requirements:

- recent source path/display name;
- last page and page count;
- last-opened timestamp;
- source type;
- open/remove/clear actions;
- missing/moved sources fail gracefully;
- configurable or fixed bounded record count;
- no passwords or content bytes.

### 4.3 Page bookmarks

Bookmarks are explicit user markers and are distinct from resume state.

Requirements:

- add/remove/toggle bookmark on current logical page;
- list/jump to bookmarks;
- visible indication in the thumbnail/page navigation UI where practical;
- bookmarks stored outside source files;
- archive/PDF/folder sources remain unmodified.

Use the same source identity scheme as reading state.

## 5. Folder provider and recursive folders

### 5.1 Folder reading

Add `Open Folder` and drag/drop folder support.

The provider should:

- enumerate supported image files;
- preserve relative paths;
- use natural ordering;
- reuse the common decoder/cache/viewer pipeline;
- support thumbnails, single/double page, LTR/RTL, resume, and bookmarks;
- avoid reading full image files until requested.

### 5.2 Safe recursive discovery

Support an option to include subfolders in the same logical reading source.

Required safeguards:

- centralized maximum discovered-entry count;
- centralized maximum traversal depth;
- deterministic natural ordering on relative paths;
- do not follow directory junctions/reparse points/symlinks in a way that can create traversal loops;
- handle inaccessible files/directories without crashing;
- stale scan results must not replace the active source after a source switch;
- cancellation or generation checks for long scans.

Recursive folder discovery is not nested archive recursion. v1.2 does not recursively open archives found inside folders or other archives.

## 6. Image decoder architecture and new formats

### 6.1 Decoder registry

Move format/backend selection behind a decoder registry or equivalent abstraction. Do not scatter extension-specific branches throughout worker/UI code.

A decoder should advertise:

- supported media formats/extensions;
- whether byte-buffer decode is supported;
- optional animation/multi-frame behavior;
- metadata/orientation handling;
- backend availability state;
- optional native runtime dependencies.

The implementation may continue to use Qt for existing formats where appropriate.

### 6.2 Target formats

v1.2 target formats:

- AVIF;
- HEIC/HEIF;
- TIFF;
- JPEG XL (`.jxl`);
- JPEG 2000 (`.jp2` and tested aliases as appropriate).

Support is gated by successful backend spike results and Windows packaging/license review. Documentation must distinguish supported from unavailable/unsupported cases rather than silently overclaiming.

### 6.3 Backend spike requirements

Before locking the implementation, verify candidate backends on Windows x64 for:

- decode from memory or safe temporary-free path where practical;
- alpha/transparency;
- EXIF/orientation behavior;
- ICC/color profile behavior where supported;
- 8/16-bit behavior where relevant;
- multi-frame/animated behavior where relevant;
- malformed-input failure behavior;
- image pixel/resource guards;
- Python 3.12 compatibility;
- PyInstaller packaging;
- installer packaging;
- redistributed DLL/native library discovery;
- license and redistribution obligations;
- package-size impact.

Record decisions in `docs/IMAGE_BACKENDS.md` and feed exact versions/notices into release packaging.

## 7. PDF provider

### 7.1 Backend direction

Use PySide6 QtPdf (`QPdfDocument` / associated rendering facilities) as the preferred v1.2 direction unless the backend spike demonstrates a blocker.

Do not implement PDF as `ArchiveProvider` or fabricate `ArchiveEntry` compression metadata.

### 7.2 v1.2 PDF scope

Required:

- open local `.pdf` files;
- page count and stable page descriptors;
- single-page display;
- double-page display;
- LTR/RTL page ordering/navigation where sensible;
- thumbnails;
- Fit Page, Fit Width, Fit Height, zoom, pan, fullscreen;
- resume/recent history;
- application-level bookmarks;
- password prompt for supported encrypted PDFs;
- no password persistence;
- high-DPI rendering;
- bounded background rendering;
- packaged Windows support.

Explicitly out of scope for v1.2:

- PDF editing;
- annotations/highlights written to the PDF;
- forms;
- signatures;
- OCR;
- text editing;
- arbitrary document export;
- becoming a general Acrobat replacement.

QtPdf text/search/bookmark capabilities may remain internal/future work unless they are needed for implementation.

### 7.3 PDF resource limits

PDF rendering must obey centralized limits. At minimum:

- maximum render pixel count;
- bounded render request queue;
- bounded decoded/rendered page cache;
- stale-render suppression after navigation/source changes;
- maximum thumbnail render size;
- clean release of document/render resources on close/source switch.

A vector page must not be allowed to request effectively unbounded raster dimensions.

## 8. Reader fit modes

Add explicit fit modes:

- Fit Page / Fit Spread (existing behavior);
- Fit Width;
- Fit Height;
- Actual Size / physical-pixel 100%.

Requirements:

- work for archive images, folder images, and PDF pages;
- work in single/double page where applicable;
- user zoom exits or temporarily overrides fit mode predictably;
- resize/high-DPI monitor changes recalculate fit safely;
- mode is reflected correctly in actions/settings/resume state.

## 9. Non-destructive border trimming

Add display-only border trimming for scanned images.

Modes:

- Off;
- Auto;
- Manual margins.

Principles:

- never modify source files/archive entries/PDF content;
- trimming is part of display/render state;
- operate within bounded CPU/memory cost;
- avoid forcing full archive extraction;
- preserve zoom/pan/fit behavior;
- handle dark/black borders and light/white borders where practical;
- manual mode provides predictable per-edge margins;
- auto mode should fail conservatively rather than cutting real artwork aggressively.

For v1.2, PDF auto-trim may be supported only if the implementation naturally reuses the rendered-image pipeline; documentation may state any source-specific limitation.

## 10. Settings and persistence

Persistent non-sensitive settings/state may use a combination of QSettings and a dedicated local data store if needed.

Use QSettings for small application preferences. If history/bookmarks/source state becomes relational or larger, prefer a versioned local data model rather than forcing everything into QSettings.

Never persist:

- archive/PDF passwords;
- decrypted content bytes;
- rendered page images unless a later explicit cache design is reviewed;
- secrets from future remote services.

Add schema/version migration tests for any new persistent data format.

## 11. Security and resource limits

v1.1 safeguards remain mandatory. v1.2 must additionally centralize/verify limits for:

- folder entry count;
- folder traversal depth;
- decoder pixel/resource bounds;
- native codec failures;
- PDF render pixels;
- PDF render queue;
- content-source page count where needed;
- history/bookmark record growth;
- thumbnail/render caches.

No v1.2 feature may introduce:

- an unbounded recursive scan;
- an unbounded worker/render queue;
- unbounded decoded images;
- persistent credentials;
- source modification;
- hidden full-document/full-folder extraction/copying.

## 12. Packaging and dependency/license decisions

v1.2 adds native-codec and QtPdf packaging risk.

Before release:

- record exact image backend versions and licenses;
- record required DLL/native runtime files;
- update PyInstaller hooks/specs;
- update installer packaging;
- update backend/self-test diagnostics;
- update third-party notices/source-license bundles;
- verify clean Windows installation without developer tools;
- keep portable and installer artifacts working independently.

## 16. Recommended implementation / Codex order

Work on one issue at a time. Preserve a runnable repository after every issue.

Recommended dependency order:

1. v1.2 parent/tracking issue and this plan.
2. ContentProvider/content-source abstraction and common page descriptors.
3. Reading-state persistence model (resume/history/bookmark storage foundation).
4. FolderContentProvider (flat folders).
5. Safe recursive folder traversal.
6. Decoder registry/refactor without adding new codecs yet.
7. Image-backend spike and `docs/IMAGE_BACKENDS.md`.
8. Implement/package new image codecs based on the approved spike.
9. PDF/QtPdf backend spike.
10. PdfContentProvider and viewer integration.
11. Resume/history UI and source restoration across archives/folders/PDF.
12. Bookmark UI/navigation integration.
13. Fit Width / Fit Height.
14. Auto/manual border trim.
15. CI/resource/security/packaging/documentation hardening.
16. Manual Windows QA and release-candidate checklist.

Independent work may proceed in parallel only when it does not bypass an unfinished architectural gate. In particular, new codecs should not be added by scattering special cases before the decoder registry is stable, and PDF should not be forced into `ArchiveProvider` while the content-source abstraction is unfinished.

## 17. Codex handoff protocol

For each v1.2 implementation issue, Codex should:

1. Read this plan, the target issue, current source/tests, and relevant v1.1 design documents before editing.
2. Work only on the target issue plus the minimum documented prerequisite/refactor.
3. Preserve read-only/local-only behavior and bounded resources.
4. Do not persist/log credentials.
5. Do not model folders/PDF as fake archives merely to avoid the new abstraction.
6. Add focused tests with each implementation.
7. Run focused tests during development, then the full pytest/Ruff/release checks relevant to the change.
8. Record backend/package/license decisions instead of assuming native redistribution is safe.
9. Keep Windows portable/installer packaging in mind for every native dependency.
10. Leave the repository runnable and documented when the issue is complete.

Suggested starting prompt:

> Implement ArchiveLens v1.2 issue #N. First read `docs/V1.2_PLAN.md`, issue #N, `docs/V1.1_PLAN.md`, the current provider/worker/viewer architecture, and relevant tests. Work only on that issue and documented prerequisites. Preserve source immutability, local-only behavior, bounded resource use, stale-result protection, credential redaction, and packaged-Windows compatibility. Add tests, run focused checks, then run the full repository checks required by the issue.
