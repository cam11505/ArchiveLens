# ArchiveLens v1.3 Development Plan

Target version: **1.3.0**

This document defines ArchiveLens v1.3 as the **macOS & Cross-platform Foundation** release. v1.2 expands what ArchiveLens can read and improves core reader continuity. v1.3 should make that functionality officially available on both Windows x64 and macOS Apple Silicon while removing Windows-only assumptions from backend, packaging, platform integration, and release verification.

## 1. Release goal

ArchiveLens v1.3 should officially support:

- Windows x64;
- macOS Apple Silicon (`arm64`).

The release is not a UI redesign and is not the advanced-library/Webtoon release. Its purpose is to establish a durable cross-platform base before those larger reader features continue in v1.4.

Primary v1.3 scope:

1. macOS compatibility/backend spike before implementation.
2. Audit and isolate Windows-only platform assumptions.
3. Cross-platform RAR/CBR backend strategy preserving current security guarantees.
4. macOS qualification for v1.2 image codecs and QtPdf.
5. macOS `.app` packaging using PyInstaller or an explicitly reviewed equivalent.
6. macOS application metadata, menus/shortcuts, drag/drop, Finder document/Open With integration.
7. Retina/high-DPI and input/path behavior qualification.
8. Developer ID signing, hardened runtime, notarization, and DMG release path.
9. macOS CI, packaged self-test, artifact verification, and release automation.
10. Windows regression protection throughout the port.
11. Final Windows/macOS manual QA and release-candidate gate.

Initial macOS release target is **Apple Silicon arm64**. Intel/x86_64 and Universal2 may be evaluated later but are not release requirements for v1.3.

## 2. v1.2 baseline that must be preserved

v1.3 assumes v1.2 provides and regression-protects:

- `ContentProvider` or equivalent content-source abstraction;
- archive providers for ZIP/CBZ, 7Z, RAR/CBR;
- folder content provider with safe recursive discovery;
- PDF content provider using QtPdf or the approved v1.2 backend;
- decoder registry plus AVIF, HEIC/HEIF, TIFF, JXL, JP2/JPEG 2000 where approved;
- resume/recent history/bookmarks;
- Fit Page/Spread, Fit Width, Fit Height, Actual Size;
- non-destructive border trim;
- single/double page, first-page cover, LTR/RTL;
- thumbnail sidebar and animated GIF;
- bounded caches/queues and stale-result protection;
- source immutability and session-only credentials;
- Windows x64 portable/installer packaging and release verification.

The cross-platform port must not weaken any v1.2 resource, privacy, credential, source-immutability, or local-only guarantee.

## 3. Cross-platform principles

### 3.1 Platform-neutral application core

Reader, content-provider, decoder, cache, reading-state, and credential behavior should remain platform-neutral whenever possible.

Platform-specific code should be isolated behind small adapters/services for concerns such as:

- native archive backend loading;
- application bundle/runtime paths;
- file association/document metadata;
- platform menu/shortcut conventions;
- release packaging/signing;
- platform-specific filesystem behavior.

Avoid scattered `sys.platform` checks throughout reader/UI business logic.

### 3.2 Direct-open remains first-class

A macOS user should be able to install/open ArchiveLens, drag or open a supported archive/folder/PDF, and read immediately without library import, cloud account, or external command-line dependencies.

### 3.3 Feature parity policy

The desired v1.3 result is practical parity for the v1.2 reader feature set across Windows x64 and macOS arm64.

If a native backend has a platform limitation, document it explicitly rather than silently changing behavior or weakening safeguards.

## 4. First gate: macOS compatibility/backend spike

Do not begin with UI polish or build-script rewrites. First run a focused spike on a real macOS arm64 environment.

Validate:

- Python 3.12+ and supported PySide6 versions;
- ordinary application startup from source;
- core Qt Widgets behavior;
- archive ZIP/7Z providers;
- current RAR/CBR implementation failure points;
- folder provider and recursive traversal behavior;
- decoder registry and every v1.2 image backend;
- QtPdf/PDF provider;
- QSettings location/behavior;
- drag/drop and file dialogs;
- Retina/high-DPI rendering;
- current PyInstaller spec assumptions;
- native library architecture and redistribution constraints;
- test suite behavior under macOS;
- source/runtime paths when frozen.

Output a versioned `docs/MACOS_BACKENDS.md` (or equivalent) recording:

- tested macOS version(s);
- tested Apple Silicon architecture;
- backend/library versions;
- binary architecture (`arm64`) status;
- packaging status;
- licensing/redistribution notes;
- blockers and selected remediation path.

The spike is the architectural gate for all later v1.3 work.

## 5. Platform abstraction audit/refactor

After the spike, remove or isolate Windows-only assumptions that affect macOS support.

Focus areas:

- build/runtime path resolution;
- native backend discovery;
- platform-specific dynamic-library loading;
- filesystem normalization and case-sensitivity assumptions;
- symlink/reparse behavior differences;
- settings/cache/data locations;
- standard keyboard shortcuts/menu roles;
- packaged self-test paths;
- release artifact naming.

Do not rewrite cross-platform code merely for symmetry. Keep the refactor narrow and test-driven.

## 6. RAR/CBR backend

The current Windows RAR path uses a Windows DLL/ABI and is the largest known platform-specific core dependency.

v1.3 must define a platform-neutral RAR backend boundary such as:

```text
RarArchiveProvider
        ↓
RarBackend
├── WindowsUnrarBackend
└── MacUnrarBackend
```

The exact class names may differ, but the provider/UI should not branch on operating system.

macOS RAR requirements:

- RAR4/RAR5 cases supported at the same documented level as the selected backend;
- CBR alias behavior;
- Unicode names;
- encrypted RAR with the existing session-only credential principles;
- password must not be passed in process command-line arguments;
- no persistent password/log leakage;
- no user-visible full extraction;
- bounded entry reads/resource accounting;
- solid archive costs respected;
- clean packaged `.app` backend discovery;
- exact redistribution/license obligations documented.

Prefer a native library/wrapper strategy that preserves memory/callback security semantics. A subprocess CLI approach must not be adopted merely for convenience if it exposes passwords or forces unsafe extraction behavior.

## 7. Image codec and PDF macOS qualification

Every image backend selected in v1.2 must be tested in a packaged macOS arm64 environment.

Target matrix:

- JPEG/PNG/WebP/BMP/GIF baseline;
- AVIF;
- HEIC/HEIF;
- TIFF;
- JPEG XL/JXL;
- JPEG 2000/JP2;
- QtPdf/PDF provider.

For each backend verify:

- arm64 native binary availability;
- decode/render from the existing pipeline;
- EXIF orientation/alpha/profile behavior already promised by v1.2;
- malformed/oversized input behavior;
- resource guards;
- thumbnail path;
- PyInstaller collection/runtime discovery;
- license/redistribution obligations;
- missing-backend error behavior.

Do not introduce a second macOS-specific decoder stack unless unavoidable. Prefer the same decoder registry and provider interfaces with platform-specific backend packaging underneath.

## 8. macOS application bundle packaging

Create an official macOS arm64 application bundle.

Target artifact:

```text
ArchiveLens.app
```

Requirements:

- launch from Finder without Python installed;
- use PyInstaller macOS bundle support or an explicitly reviewed equivalent;
- include required Qt frameworks/plugins and approved native codec/archive runtimes;
- no external Homebrew/MacPorts/manual package requirement for end users;
- proper bundle identifier;
- application icon/assets;
- version metadata;
- release resources/notices/licenses included appropriately;
- packaged self-test can locate every required backend;
- startup and source switching work outside the source checkout.

Keep Windows packaging scripts functional; shared release metadata should not require duplicate manual version edits where avoidable.

## 9. macOS application integration

### 9.1 Menus and shortcuts

Use Qt standard keys/menu roles where practical so macOS receives platform-appropriate behavior, including Command-key conventions.

Validate:

- Open;
- Settings/Preferences placement;
- About ArchiveLens placement;
- Quit;
- fullscreen;
- bookmark and reader shortcuts;
- existing LTR/RTL logical navigation.

### 9.2 Finder document integration

Declare supported document types in the application bundle/Info.plist as appropriate so Finder can offer ArchiveLens through Open With and launch files into the application.

Target types include the actually supported v1.3 set such as:

- `.cbz`;
- `.cbr`;
- `.zip`;
- `.rar`;
- `.7z`;
- `.pdf`;
- supported direct image types where the product chooses to expose them.

Do not forcibly take over defaults.

Validate drag/drop of files and folders into the app.

## 10. Retina, high-DPI, paths, and interaction qualification

macOS needs explicit validation rather than assuming Windows DPI behavior maps exactly.

Test:

- Retina 2x rendering;
- Fit Page/Width/Height;
- Actual Size / physical-pixel 100% semantics;
- thumbnail sizing;
- PDF render resolution and cache identity;
- moving between displays/scaling modes;
- trackpad scroll/pan/zoom interactions where existing viewer handling receives them;
- Unicode filenames;
- case-sensitive/case-insensitive filesystem behavior where practical;
- long/nested paths;
- symlink traversal safety in folder recursion;
- external/removable volume disappearance;
- source identity/history behavior for mounted volumes.

Any platform-specific semantic difference should be documented and covered by tests where deterministic.

## 11. Signing, hardened runtime, notarization, and DMG

For official public macOS releases, build a proper Developer ID distribution path.

Target flow:

```text
ArchiveLens.app
  ↓
Developer ID Application signing
  ↓
Hardened Runtime / reviewed entitlements
  ↓
notarization
  ↓
staple verification
  ↓
ArchiveLens-<version>-macos-arm64.dmg
```

Requirements:

- keep secrets/certificates out of the repository;
- CI/release jobs consume signing/notarization credentials from protected secret storage;
- support an unsigned/ad-hoc local developer path where appropriate;
- official release artifacts are Developer ID signed and notarized when credentials are configured;
- verify signatures and notarization ticket as part of release checks;
- document the manual prerequisites for maintainers, including Apple Developer Program/certificate setup;
- DMG provides a conventional drag-to-Applications experience where practical.

Do not block ordinary source development on Developer ID credentials.

## 12. CI and release automation

Add macOS CI without weakening existing Windows CI.

At minimum macOS jobs should cover:

- pytest;
- Ruff/source checks as applicable;
- backend availability/self-tests;
- build `.app`;
- packaged self-test;
- representative ZIP/7Z/RAR/folder/PDF/new-codec smoke fixtures;
- bundle architecture inspection;
- signature verification when applicable;
- DMG/release artifact verification.

Release-tag workflow should be able to produce, verify, and publish platform-specific artifacts independently so one platform failure is visible and does not silently produce a partial/incorrect release.

Do not attempt Windows-to-macOS cross-compilation for the official `.app`; build and test the macOS artifact on macOS.

## 13. Release artifacts

Target v1.3 release outputs:

```text
ArchiveLens-1.3.0-windows-x64.zip
ArchiveLens-1.3.0-setup-x64.exe
ArchiveLens-1.3.0-macos-arm64.dmg
```

Source/wheel/sdist/license/source-bundle artifacts may continue according to the existing release policy.

macOS Intel/x86_64 and Universal2 are not required for v1.3.

## 14. Security and privacy regression requirements

Cross-platform work must preserve:

- no telemetry;
- no mandatory cloud/account;
- source files are read-only;
- no archive/PDF passwords in settings/logs/command-line arguments;
- no hidden full-archive extraction to visible directories;
- bounded archive/folder/PDF/image resources;
- stale-result protection;
- no persistent decrypted page cache introduced by packaging/platform code.

Native backend convenience must never take precedence over these guarantees.

## 19. Codex handoff protocol

For each v1.3 issue, Codex should:

1. Read this plan, `docs/V1.2_PLAN.md`, the target issue, current implementation, and relevant tests before editing.
2. Work on one issue plus only documented prerequisites.
3. Treat the compatibility/backend spike decisions as authoritative unless a new blocker is documented.
4. Keep application-core reader/content logic platform-neutral wherever practical.
5. Preserve local-only/read-only behavior, ephemeral credentials, bounded resources, stale-result protection, and source immutability.
6. Do not replace secure in-process/backend behavior with unsafe subprocess/password command-line shortcuts.
7. Keep Windows x64 behavior green while adding macOS arm64 support.
8. Add platform-specific tests only where behavior genuinely differs; otherwise prefer shared tests.
9. Run focused tests, then full checks appropriate to the issue on the affected platforms.
10. Update backend/license/packaging documentation whenever native dependencies change.
11. Leave the repository runnable after every issue.

Suggested starting prompt:

> Implement ArchiveLens v1.3 issue #N. First read `docs/V1.3_PLAN.md`, `docs/V1.2_PLAN.md`, issue #N, and the relevant current architecture/tests. Work only on that issue and its documented prerequisites. Preserve local-only/read-only behavior, bounded resources, credential redaction, source immutability, and Windows x64 compatibility while establishing macOS arm64 support. Follow the backend/platform decisions already recorded by earlier v1.3 issues. Add tests and run the required focused/full checks.
